topic: Import pre-existing Stalwart domains and mailboxes into a tenant account
updated: 2026-09-28T19:42

- (note) Source: user chat description of feature idea, no prior source doc. Codebase research via Explore agent confirmed grounding facts (see below).
- (note) Existing platform: backend/src/api/tenant.routes.ts creates domains via stalwartClient.createDomain (JMAP Domain/set), falls back to listDomains() on StalwartDomainExistsError to adopt an existing Stalwart domain id into a local DomainModel doc. Same adoption pattern already exists for the create-collision case.
- (note) backend/src/stalwart/client.ts already has listDomains() (line 303) and listAccounts() (line 840) returning ALL Stalwart domains/accounts unscoped to any tenant -- the list primitives this feature needs already exist, no new Stalwart-side API work required.
- (note) backend/src/api/platform-tenant.routes.ts has GET /unmanaged-domains, Super-Admin only, diffing listDomains() against tracked DomainModel docs. No tenant-admin-facing equivalent, and no unmanaged-mailboxes/accounts endpoint at all yet.
- (note) Domain.domainName and Mailbox.address both carry a GLOBAL unique index (not per-tenant) -- an unmanaged Stalwart domain/mailbox can only ever be imported by one tenant, and the search/import feature must exclude anything already claimed by another tenant's local record.
- (note) Imported mailboxes come from Stalwart accounts created outside the platform, so the platform never learns their password -- MailboxModel.createMailbox today always sets a password at creation time, which import cannot supply.
- (capability) CAP-1 intent: tenant admin can search Stalwart-side domains not yet tracked by any tenant, by typing a domain name/substring, from the tenant detail view's Domains section. success: search returns only domains that exist in Stalwart (via listDomains) and have no local DomainModel record, matching the typed substring; a domain already claimed by any tenant (including this one) never appears.
- (capability) CAP-2 intent: tenant admin can select one or more of those searched unmanaged domains and import them in one action, creating a local DomainModel doc per selected domain linked via stalwartDomainId, owned by the current tenant. success: after import, each selected domain has exactly one DomainModel doc with tenantId set to the current tenant and stalwartDomainId matching the Stalwart record; no Stalwart-side write occurs (Stalwart data is untouched).
- (capability) CAP-3 intent: importing a domain also discovers and attaches that domain's existing Stalwart mailboxes/accounts to the tenant as local MailboxModel docs. success: after import, every Stalwart account belonging to the imported domain (via listAccounts filtered by domainId) has exactly one MailboxModel doc with tenantId/domainId set and stalwartAccountId matching the Stalwart record; mailboxes already claimed by another tenant are skipped, not duplicated or reassigned.
- (capability) CAP-4 intent: once imported, the tenant admin views and manages the domain and its mailboxes through the exact same UI/APIs as a platform-created domain (no separate 'imported' screen or reduced action set). success: an imported domain/mailbox appears in the normal domains/mailboxes list and detail views and supports the same actions (status toggle, DKIM view, mailbox settings, etc.) available to a platform-created one.
- (constraint) Import must reuse the existing global-uniqueness invariant on Domain.domainName and Mailbox.address: a domain or mailbox already owned by any local record (this tenant or another) must never be re-importable or reassignable through this feature.
- (constraint) Import performs no Stalwart-side writes (no create/update/delete JMAP calls) -- it only reads via listDomains/listAccounts and writes local DomainModel/MailboxModel docs pointing at the existing Stalwart ids, mirroring the current StalwartDomainExistsError adoption fallback already used for domain creation.
- (constraint) Imported mailboxes have no platform-known password (they were created directly on Stalwart). The mailbox record must be created without asserting a password the platform invented, and the tenant admin/end user must go through a password-reset/set step before the mailbox is usable through platform-issued credentials.
- (constraint) Search/import for unmanaged domains must be tenant-admin-facing (not Super-Admin-only like the existing /unmanaged-domains endpoint), but must not expose or leak any other tenant's already-claimed domains/mailboxes -- only globally-unclaimed Stalwart records are eligible candidates.
- (non_goal) Not migrating or copying actual mail content (existing messages, IMAP folders/labels) -- import only registers existing Stalwart domain/account ids as local metadata records; the mail data stays exactly where it is on Stalwart.
- (non_goal) Not building a general bulk sync/reconciliation engine -- that already exists read-only in reconciliation.service.ts; this feature is a one-time, admin-triggered, per-selection import action, not an ongoing sync.
- (non_goal) Not allowing a domain or mailbox already owned by another tenant's local record to be reclaimed, transferred, or moved between tenants through this feature.
- (question) Open: how is domain ownership verified before a tenant admin is allowed to claim an unmanaged Stalwart domain? Domains/mailboxes are sensitive -- without some proof of ownership (e.g. DNS TXT challenge, or platform-admin-mediated approval), any registered tenant could self-serve claim any client's pre-existing domain+mailboxes found via search. Input did not specify a verification step.
- (question) Open: what happens to an imported mailbox's password/login -- is the end user forced through a reset-password flow immediately, does an admin set a temporary password at import time, or is the mailbox left password-less/disabled until explicitly reset?
- (question) Open: does the search UI need extra metadata per unmanaged domain (mailbox count, creation date) to help the admin identify the right domain, or is a name match sufficient?

All 4 capabilities have intent+success stated as WHAT not HOW; all 4 constraints each rule out a concrete design choice; 3 non-goals present; success signal is a concrete, demonstrable scenario; CAP-1..4 ids unique; prose lean, no decoration.

No wrapper-only content dropped.

- (decision) User confirmed: the search/select/import action is performed by the platform Super-Admin from a tenant's detail view in the admin panel (extending the existing Super-Admin-only /unmanaged-domains screen), not by the tenant admin self-serving from their own dashboard. This resolves the open question on domain-ownership verification -- a trusted super-admin manually curates which Stalwart domain maps to which tenant, so no automated verification (DNS challenge etc.) is required.
- (capability) CAP-1 revised actor: Super-Admin, not tenant admin. intent: platform Super-Admin, from a given tenant's detail view, can search Stalwart-side domains not yet tracked by any tenant. success unchanged: search returns only domains with no local DomainModel record, matching the typed substring; a domain already claimed by any tenant never appears.
- (capability) CAP-2 revised actor: Super-Admin selects one or more searched unclaimed domains and imports them into the tenant being viewed. success unchanged.
- (constraint) Revised: search/import is Super-Admin-only, performed from the tenant detail view in the admin panel -- it extends the existing Super-Admin-gated surface (platform-tenant.routes.ts) rather than becoming tenant-admin self-service. Superseded the earlier draft constraint that framed this as tenant-admin-facing.
- (event) SPEC.md re-derived after Super-Admin-actor correction: CAP-1/CAP-2 intents and the tenant-facing constraint updated to Super-Admin acting from a tenant detail view; the domain-ownership-verification open question closed (Super-Admin's manual selection substitutes for automated verification) and removed from Open Questions; password-handling and search-metadata open questions retained.
- (decision) User resolved open question: imported mailbox passwords stay exactly whatever they already are in Stalwart -- no reset, no temp password, no disabling. Platform does not need to know/store the plaintext password; the mailbox is immediately usable with its existing Stalwart credentials post-import.
- (decision) User resolved open question: search results list domain names only, no extra metadata (mailbox count, creation date, etc).
